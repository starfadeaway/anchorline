# B 臂切片封顶实验（2666 字符）——结论：**不采用**

> 日期：2026-11-12
> 背景：评审 N1/N2 指出 B 臂索引未做长度封顶（中位 49k、最长 968k 字符），4k 预算下 154/154 题都顶满后被截断；建议把单条切片上限按 `预算 ÷ top_k ≈ 2666` 字符推导。
> 本文件记录该建议的实测结果：**照做会让 B 臂显著变差**，因此已回退。

## 实验设置

| 项 | 值 |
|---|---|
| 索引 | `v2_web_slices`，1737 条，`_cap_head(text, 2666)` 保头截断 + `…(截断)` 标记 |
| 实测切片长度 | min 2463 / median 2664 / max 2664（重建后） |
| 题目 | 154（确定性 web 题，seed=42，与报告同一批） |
| reader | `deepseek-flash`，temperature 1.0，判定用确定性判分 |
| 预算 | 4k tokens（chars/4），top-6，`assemble_blocks` |
| 对照 | 旧索引（不封顶）：`b_arm_154_run3.json`（57.14%，88/154） |

## 结果

| 指标 | 不封顶（旧） | 封顶 2666（新） |
|---|---|---|
| B 准确率 | **57.14%**（88/154） | **43.51%**（67/154） |
| 配对差（新−旧） | — | **−13.64pp** |
| 精确符号翻转 p | — | **0.0011**（显著变差） |
| 变化题数 | — | 39 / 154 |
| 实际注入 token | 4000 | 4000 |

## 解释

4k 预算下，**top-1 切片本身信息量最大**：旧行为把 top-1 截到 16k 字符（4000 tokens），保留了最多相关上下文；封顶 2666 后，top-1 只剩 666 tokens 左右，其余 5 条相关性更低的切片反而挤进来。也就是说，N1 的"截断让 B 吃亏"在数值上不成立——恰恰相反，**把预算尽量给最相关的那一条**更好。

## 决定

1. **不采用 2666 封顶**；`build_baseline_index.py` 的默认上限改为 `4000 * 4 = 16000` 字符（= 预算字符数，等效于旧的有效行为，同时把 49k/968k 的极端切片挡住），`ANCHORLINE_INDEX_SLICE_CAP` 可覆盖。
2. 索引已恢复为旧版（1737 条，max 967757）——B 的数字与报告保持不变，**无需重跑 168**。
3. 2666 封顶的索引与结果保留为证据（均不入库）：
   - `data/backups/v2_web_slices_cap2666.lance`
   - `data/eval/_drafts/b_arm_154_rebuild.json`（43.51%）
4. 结论写进 README 的「B 臂口径」：封顶实验测过、结果为负、默认按预算字符数封顶。

> 备注：这次实验本身消耗 1737 次 embedding + 154 次 reader 调用；它换来的是一个可复现的负结果，而不是又一处"看起来修好了"的改动。
