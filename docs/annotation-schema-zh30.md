## 1. 定位（先说清它不干什么）

| 它是什么 | 它不是什么 |
|---|---|
| 原生中文的**冲突裁决规则验证集** | ❌ 准确率测试集 —— **不报准确率** |
| 检查记忆层的裁决逻辑是否符合预期（覆盖 / 并存 / 标失效 / 升级人工） | ❌ 与公开集可比 —— 不能和 LongMemEval 分数并列 |
| **两条消融轴的唯一可验证集**：「时间优先」「来源可信度分级」在主集上均无区分度（见 `annotation-protocol-ku78.md` §2） | ❌ 大样本统计 —— 单条翻转即改变 3.3 个百分点 |
| 30 条，覆盖 3 种冲突类型 × 4 种裁决方式 × 3 个正交标记（时间戳形态 / 问句形态 / 来源通道） | ❌ 无偏评测集 —— **构造偏置无法完全排除**，见 §7.5 |

> **报告里的固定措辞**：「自建 30 条中文冲突集用于验证裁决规则是否按预期触发，不用于报告准确率；准确率只报 LongMemEval-S 主集。」

## 2. 覆盖矩阵（30 条的分配）

| 冲突类型 ↓ / 裁决方式 → | 覆盖 | 并存 | 标失效 | 升级人工 | 小计 |
|---|---|---|---|---|---|
| **时效**（旧值被新值取代） | 6 | 3 | 2 | 1 | 12 |
| **语义**（同一事实的表述细化/修正） | 4 | 2 | 2 | 1 | 9 |
| **偏好反转**（用户明确改变偏好） | 4 | 1 | 1 | 1 | 7 |
| **无冲突**（记忆正常召回，不该触发裁决） | — | — | — | — | 2 |
| **小计** | 14 | 6 | 5 | 3 | **30** |

**设计意图**

- 「覆盖」最多（14 条）—— 这是真实场景的主路径；
- 「升级人工」最少（3 条）—— 但**必须存在**，否则「低置信才升级人工」这条规则永远没被验证过；
- 保留 **2 条无冲突**，专门验证**不误触发**：记忆层不该在没冲突时乱裁决（过度裁决是这类系统的常见失败模式）。

### 2.1 正交标记：30 条还必须带上这 3 个维度

> **为什么必须加**：首版 zh30 按「旧值先、新值后、时间戳一致」构造，等于**构造规则偏向「时间优先」** —— 策略只要照着时间戳选就天然全对，测不出任何东西（**送分题**）。
> 同时，主集（ku78）上「来源可信度」也**零方差**（156/156 gold session 同源族 `answer_*`），这一轴在主集上同样没有可分性。
> **所以 zh30 必须成为这两个轴的唯一可验证集 —— 这两条轴现在都归 zh30 管。**

| 正交标记 | 取值 | 条数要求 | 测什么 |
|---|---|---|---|
| `timestamp_mode` | `forward`（旧值时间戳更早）/ **`reverse`（旧值时间戳更晚）** / `none`（无时间戳） | **reverse 至少 6 条**、none 至少 4 条、forward 最多 20 条 | 「时间优先」策略。**没有 reverse 这一档，时间优先在 zh30 上就是送分。** |
| `query_form` | `current`（问当前值）/ **`retrospective`（问旧值）** | **retrospective 至少 4 条** | 「回溯意图识别」能力（主集 1b 层的那条轴，在 zh30 上再验一次，且可控） |
| `source_channel` | `user_chat` / `doc` / `tool_output` / `third_party` | **异源组合至少 8 条**（两侧 channel 不同） | 「来源可信度分级」。**同源组合（两侧都是 `user_chat`）在这条轴上无信息，必须保证异源条数够** |

**反向时间戳（`timestamp_mode=reverse`）的正确构造**（这一条最容易被写错）：

- 问句问的是**当前值**（`query_form=current`），期望答案是**新值**；
- 但**新值所在消息的时间戳更早**，旧值所在消息的时间戳更晚；
- 这样「按时间戳选较晚的」会选到旧值 → **策略在这里必须输**；
- 如果只把时间戳顺序反过来、问句也跟着改成问旧值，就退化成送分题 —— **问句形态与时间戳方向必须解耦**。

**retrospective 用例的正确构造**：问句明确问旧值（「我之前常住的城市是？」），且旧值在较早的消息里 → 期望答案是**旧值**。这类用例验证的是「读到回溯限定词时回取旧值」，**不是**「时间优先」。

### 2.2 与 30 条主矩阵的关系

主矩阵（冲突类型 × 裁决方式）不变，仍为 30 条；上面 3 个正交标记是**叠加在这 30 条上的标签**，不额外增加条数，但**必须按上表配额分配**。分配表随用例一并落盘（`zh30.jsonl` 的 `timestamp_mode` / `query_form` / `source_channel` 三列）。

## 3. 字段 schema

每条一行，`data/annotations/zh30.jsonl`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `case_id` | str | 自编号，如 `zh30-001` |
| `lang` | str | 固定 `zh` |
| `entity` | str | 被更新的属性名（如「常住城市」） |
| `conflict_type` | enum | `时效` / `语义` / `偏好反转` / `无冲突` |
| `expected_resolution` | enum | `覆盖` / `并存` / `标失效` / `升级人工` / `不裁决` |
| `stale_value` | str | 旧值（**具体值**，不是整句） |
| `new_value` | str | 新值（具体值） |
| `stale_session` | str | 说出旧值的那一轮消息 id |
| `new_session` | str | 说出新值的那一轮消息 id |
| `source_confidence` | int | 1..5，来源可信度分级 |
| `timestamp_mode` | enum | `forward` / `reverse` / `none` | **时间戳与语义方向的关系**（见 §2.1）。`reverse` = 旧值的时间戳反而更晚。 |
| `query_form` | enum | `current` / `retrospective` | **问句形态**。`retrospective` = 问旧值。 |
| `source_channel` | enum | `user_chat` / `doc` / `tool_output` / `third_party` | **来源通道**，用于「来源可信度分级」的对照（旧值与新值通道不同才有意义） |
| `match_mode` | enum | `exact` / `normalized` / `fuzzy` |
| `query` | str | 测试问句 |
| `gold_answer` | str | 期望答案（应含新值、不含旧值；`query_form=retrospective` 时相反） |
| `note` | str | 设计意图备注 |

**与 ku78 完全同构** —— 判定器可以共用一套匹配逻辑，只是匹配对象不同。

## 4. 构造规则（硬约束）

每条用例必须同时满足：

1. **旧值先、新值后**：两个消息按时间排序，`stale_session` 早于 `new_session` —— **但这是 `timestamp_mode=forward` 的默认做法，不是硬约束**。`reverse` 用例必须**故意违反**它（旧值的时间戳更晚），否则策略照时间戳选就天然全对，测不出东西（见 §2.1）；
2. **同一属性**：`stale_value` 与 `new_value` 必须是同一 `entity` 的两个取值，不是两件不同的事；
3. **新值不重复出现**：除 `new_session` 外，不允许其他消息再提到该属性（否则「标失效」和「并存」的判定会含混）；
4. **问句必须只指向该属性**：`query` 不能同时问别的属性，否则答对了一半也算「用了过期事实」，指标会失真；
5. **旧值必须是「具体值」**：不能是整句。例：`居住城市=上海` → `居住城市=北京`；不能写「他之前说过住在上海，后来又说了别的」；
6. **无冲突的 2 条**：`stale_value` 与 `new_value` 相同或不存在，`expected_resolution` 固定为 `不裁决`；
7. **问句形态与时间戳方向必须解耦**：`timestamp_mode=reverse` 的用例，问句仍问**当前值**；`query_form=retrospective` 的用例，时间戳仍为 `forward`。**两者混在一起就退化成送分题**；
8. **异源配额**：`source_channel` 两侧不同的用例不少于 8 条，否则「来源可信度分级」这条策略在 zh30 上同样无区分度（主集上已经零方差，不能在 zh30 上再零方差一次）。

### `source_confidence` 分级定义（判定「升级人工」要用）

| 分值 | 含义 |
|---|---|
| 5 | 用户明确断言（"我现在住在北京"） |
| 4 | 用户明确陈述但有修饰语（"我搬到北京了，应该算常住吧"） |
| 3 | 用户在相关话题里顺带提到（"昨天去北京出差"） |
| 2 | 第三方转述或推测（"他好像搬去北京了"） |
| 1 | 含糊或可能是玩笑（"要是住北京就好了"） |

**规则**：新旧两条来源可信度**都 ≥ 4** → 按时间优先裁决；**任一条 ≤ 2** → `升级人工`。
（这个阈值本身是消融臂之一。）

## 5. 中文特有的三个坑（写用例时必须避开）

1. **同义改写**：「北京」vs「首都」vs「京城」—— `fuzzy` 匹配会命中，但 `exact` 不会。这正是要在 ku78 上做阈值敏感性分析的原因。
2. **称呼漂移**：用户可能先说「我老家在武汉」后来改口说「我户籍还在武汉但常住地是深圳」—— 这是「**并存**」而不是「覆盖」，因为两个维度不同（户籍 vs 常住）。用例的 `entity` 必须写清楚是哪个维度。
3. **否定与转述**：「我不是住上海了」是**语义**冲突且否定优先；「我朋友住上海」**不是**用户属性（写入过滤应拦掉）—— 后者用 `conflict_type=无冲突` + `expected_resolution=不裁决` 来测**写入过滤**。

## 7. 已知边界

1. **用例由同一人构造与验证** —— 可能与标注者对「什么叫冲突」的直觉一致，外部视角缺失。缓解：报告写明用例构造规则全文，读者可据此判断。
2. **30 条不足以做统计推断** —— 只做「分支是否被正确触发」的定性验证，不做比率比较。
3. **中文语义歧义高于英文** —— §5 的三个坑是已知失败点，用例设计时刻意覆盖，但覆盖率必然不全。
4. **`expected_resolution` 含设计判断** —— 「覆盖 vs 并存」的边界取决于记忆层的语义定义，ADR 里必须把这个定义写死，否则用例标注无意义。
5. **构造偏置是这个集最大的风险** —— 用例由自己构造，「时间优先会不会赢」在很大程度取决于怎么构造。**首版规则（时间戳必然与语义一致）就是一个送分设计**，本版用 `timestamp_mode=reverse` 配额修掉，但**残余偏置仍在**：读者无法完全排除「反向用例仍然是按预期挑的」。
   缓解：① 配额写死并落盘；② 报告写明构造规则全文（§4 全部 8 条）供读者独立判断；③ 明确写出「两条消融轴的结论只以 zh30 为依据，zh30 是构造性验证集」。
6. **zh30 不报准确率也不做统计推断** —— 只报「分支是否按预期触发」与消融臂的**方向**（策略 A 是否优于策略 B），不报比率差异的显著性。
